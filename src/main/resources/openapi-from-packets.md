# Create or update OpenAPI from Burp packets

Use the connected project's packet database as evidence. You, the agent, author the OpenAPI document; the Burp extension stores and displays it. Never infer a complete API from one response.
If the user authorizes an active request, route the HTTP client through the configured Burp Proxy listener so the request appears in Proxy HTTP history. Verify the listener address in Burp; do not assume port 8080 is always active. This MCP server does not expose direct HTTP send tools.

1. Call `load_project_config` with the user-provided `config.yaml` path, then `start_packet_capture`. Use `get_project_storage`, `get_db_info`, and `get_db_schema` to confirm the effective directories and database. Do not choose a target or project path from observed traffic.
2. Choose the host the user requested. For example, `cafe.naver.com` is only a host filter; it is not permission to send requests. Start with `get_api_inventory` and `get_packet_delta` metadata. Use `query_burp_database` only when a question needs additional columns; then use a stable `ORDER BY id`, bounded `maxRows`, and `offset` until `hasMore` is false.
3. Group captured API packets by method and path shape. Exclude static resources such as JavaScript, CSS, images, fonts, source maps, and other assets from OpenAPI `paths`; use both URL and MIME/purpose so an API endpoint is not discarded solely because its payload resembles a file. Keep the original URL and packet IDs as evidence. Treat numeric and UUID-like segments as possible variables; do not turn ordinary string segments into variables without multiple observed values at the same position.
4. Call `list_openapi_specs` and `get_openapi_spec` for the host before editing. Preserve existing descriptions, operation IDs, tags, schemas, and manually reviewed choices unless packet evidence warrants a change.
5. For large databases, call `get_packet_delta` with `afterChangeSeq=0`, then persist and reuse `lastChangeSeq` and `databaseId` (`expectedDatabaseId` on the next call) to process only new packet metadata. Use `get_api_inventory` for a host's observed route summary; follow `nextCursor` until it is absent. Then read representative packets with `get_packet` or `save_packets`: different status codes, request body forms, and response shapes. Compare multiple samples before deciding required fields or path parameters. Put actual observed, non-sensitive values in parameter and media-type `example` fields. Never insert placeholder values such as `example`, `string`, or `0` when no value was observed; omit the example instead. Do not copy authorization headers, cookies, tokens, or personal data into examples.
6. Write or update OpenAPI 3.x with absolute HTTP(S) `servers` for the observed protocol, host, port, and any base path, plus observed paths and methods, parameters, request bodies, and response status/schema variants. Multiple servers in one file imply the same documented operations are available on each unless a path or operation overrides `servers`; use those overrides for port-specific operations. If the same method and path behaves differently by port, write separate host-specific specifications rather than merging conflicting definitions. Write human-readable titles and all descriptions in Korean; keep protocol identifiers, paths, parameter names, and schema keys as observed. If an endpoint's purpose is unclear, leave its operation `summary` and `description` empty rather than guessing. The result must reflect observed traffic, not an exhaustive API inventory. On each operation, add `x-burp-history-refs` as a list of `{historyId, packetId}` pairs from `packet_history_refs`. Query `SELECT history_id, packet_id FROM packet_history_refs WHERE packet_id IN (...)` for the DB packets chosen as evidence. Verify each referenced packet's protocol, host, and port against the operation's effective server. `historyId` is the **Burp Proxy HTTP history number displayed to the user**. `packetId` is only a disambiguating storage key: Burp can reuse a History number after a project/session restart, and the packet database may contain both records. Example: `x-burp-history-refs: [{historyId: 203, packetId: 278}, {historyId: 114, packetId: 216}]`. Do not use a bare History number or visual row position as a reference. Include at most 20 distinct, verified pairs per operation, newest saved packet first, while covering distinct documented status codes or message shapes. Omit the field when no History reference exists. Recheck each pair against the connected database when updating a spec. The Swagger viewer sorts by packet recency and displays only the latest 20 valid pairs; buttons show only History numbers.
   Burp can assign History number `0` to the first request. Keep `{historyId: 0, packetId: ...}` when it matches the saved packet.
7. Write `<host>.yaml` into the configured `storage.openapi_dir`. When separate specs are needed for different behavior on different ports of the same host, use a portable key such as `<host>--https--12345.yaml`, set its `servers` URL to the actual host and port, and pass that filename stem as `host` to the OpenAPI MCP tools. Use a temporary file and rename it into place to avoid exposing a half-written YAML file. Call `validate_openapi_spec` for structural checks and fix reported errors. The Swagger tab reloads it automatically. If an existing file changed while editing, reread and reconcile before replacing it.

Inspection results are managed separately from OpenAPI YAML in the connected packet database. Before tagging, use `list_openapi_specs` to get the exact YAML filename stem and `get_openapi_spec` to inspect the operation. In `list_endpoint_tags`, `set_endpoint_tag`, and `get_endpoint_tag_history`, `host` means that filename stem (including a `--https--12345` suffix when present), not the network hostname. `method` and `path` identify the exact OpenAPI operation; use its template path such as `/users/{id}`, not a captured URL. `serverUrl` is required when setting or clearing a tag: pass the operation's exact effective server URL, including scheme, host, port, and any base path (for example `https://example.com:443/v1`). Check that the packet evidence belongs to that operation and server before setting a tag; the MCP does not judge vulnerabilities. `VULN` means a confirmed vulnerability. `SUSPECT` means a potential issue awaiting verification, not a confirmed vulnerability. `SAFE` means the endpoint was reviewed and no issue was identified in that review; it is not a guarantee of security. Leave unreviewed endpoints untagged. Read `get_endpoint_tag_history` when reviewing a changed decision. The Swagger tab shows tags next to endpoint paths, and users can change them and view history with a right-click. Existing origin-only tags apply only to the root server, not automatically to servers with a base path; review and reapply any such decisions deliberately.

For large databases, work in pages and inspect representative packets instead of sending every full body through the model. The agent and Burp extension run on the same PC and share the configured OpenAPI directory; the MCP server does not write the OpenAPI document.
